## Locked Decisions (from SPEC + spike CONTEXT)

1. **fourCC = `MAKE_NJ_FOURCC('H','2','6','4')` = 0x34363248 LE.** Spike Q7' confirmed wire bytes `0x48 0x32 0x36 0x34` match NinjamZap's test harness.
2. **API mirrors NinjamZap verbatim** (`njclient.h:205-216`): `RawDataSendBegin(outGuid[16], fourcc, chidx, estsize)` + `RawDataSendWrite(guid[16], data, len, isEnd)` + `RawDataCallback(userData, eventType∈{0,1,2}, guid, fourcc, username, chidx, data, dataLen)`.
3. **Send-queue thread-safety = SPSC.** Spike Q3 confirmed `Net_Connection::Send` at `src/core/netmsg.cpp:289` is not thread-safe (`m_sendq.Add` unmutexed). Mutex around `Send` defeats 15.1's lock-free audio path.
4. **LGPL flags:** `--disable-gpl --disable-libx264 --enable-libopenh264 --disable-xlib --disable-libxcb --disable-sdl2 --disable-everything --enable-libopenh264 --enable-encoder=libopenh264 --enable-decoder=h264 --enable-protocol=file --enable-demuxer=h264 --enable-muxer=h264 --enable-parser=h264 --enable-swscale`. Order matters: `--disable-everything` MUST precede `--enable-*`.
5. **Cisco openh264 v2.1.1** is the last release with prebuilt mac dylibs. x86_64 platforms use prebuilts. arm64-mac falls back to (a) source build (loses MPEG-LA royalty inheritance) or (b) VideoToolbox via libavcodec's transitive dep — recommend (b).
6. **Unknown fourCC at line 2148** dispatches to `RawDataCallback` if registered, else log+discard. Never routes to `start_decode`.
7. **Additive only.** No deletes, no entitlements, no `juce_add_plugin` edits, no codesign-block edits, no `juce/video/` or `companion/` touches. Existing video stack byte-identical.
8. **Scope-deviation guard:** any plan touching `juce/video/`, `juce/JamWideJuce*.cpp`, `juce/ui/`, `companion/`, `JamWide.entitlements`, `juce_add_plugin` block, or `CMakeLists.txt:244-269` codesign block STOPS — those belong to v1.3.

## Landmines and Pitfalls

The planner MUST encode these into plan task `read_first` / `truths` fields.

**L1. fourCC byte-order — always use `MAKE_NJ_FOURCC`, never a hex literal.** `MAKE_NJ_FOURCC('H','2','6','4')` evaluates to `0x34363248` as a `uint32_t`; serialized LE on the wire as `0x48 0x32 0x36 0x34` = `'H','2','6','4'`. Anyone writing `0x48326434` ("readable hex") gets reversed bytes. The `is_video_fourcc()` impl in `usercon.cpp:108-112` reads byte-0=LSB, byte-3=MSB — correct for the `uint32_t-LE-on-wire` convention. Spike Q7' confirmed.

**L2. `Net_Connection::Send` is NOT thread-safe; drain MUST stay on the run thread.** `src/core/netmsg.cpp:289` mutates `m_sendq` without locking. The audio path calls `m_netcon->Send` from the run thread already (encoder loop at `njclient.cpp:2520-2526`). The new drain in `NJClient::Run` is safe because it's the same single sender. **Trap:** if any task moves the drain to a JUCE timer or `MessageManager::callAsync`, it concurrently mutates `m_sendq` with the audio-encoder send path → queue corruption. Drain MUST live inside `NJClient::Run()`'s body, in the same lexical scope as existing audio-encoder `Send` calls.

**L3. `m_netcon` is torn down before per-channel state during Disconnect.** 15.1-07b stabilization commit 1633bfd documented this: `NJClient::Run` runs one tick after Disconnect nulls `m_netcon` but before audio-thread shutdown. The new drain has the same vulnerability — it calls `m_netcon->Send`. Fix: guard the drain with `if (m_netcon)` at the top; drop queued items (delete `RawDataQueueItem` + free `WDL_HeapBuf`) without sending; increment drop counter.

**L4. Don't accidentally KEEP feeding unknown fourCC to Vorbis.** Today's behavior (`njclient.cpp:2148-2160` + `njclient.cpp:2680-2684`): any non-zero, non-FLAC fourCC → `CreateNJDecoder()` (Vorbis). NinjamZap's fix re-orders branches so `dib.fourcc != NJ_ENCODER_FMT_TYPE && RawData_Callback` is checked FIRST. **Trap:** if planner phrases this as "replace the existing branch", OGGv playback breaks. Correct phrasing: "INSERT a new branch ahead of the existing `else if (dib.fourcc)`". Existing branch handles OGGv+FLAC and MUST be preserved.

**L5. openh264 v2.1.1 install_name is hardcoded to `/usr/local/lib/libopenh264.6.dylib`.** Without `install_name_tool -id @rpath/...` rewrite, libavcodec at runtime dlopens the system path. Current `build_ffmpeg_lgpl.sh:170` does this for macOS. **Trap when extending to other platforms:**
- Linux: `patchelf --set-soname libopenh264.so.7 ...`; inter-dylib refs use `patchelf --replace-needed`.
- Windows: typically ship .dll next to consumer; no rewrite needed.
- The existing macOS loop at lines 178-194 rewrites inter-dylib refs via `install_name_tool -change` — replicate the equivalent per platform.

**L6. Apple-clang `/usr/local/include` shadowing affects ALL consumers.** Spike Risk #1: any consumer with homebrew ffmpeg installed links against vendored dylibs but compiles against `/usr/local/include/libavcodec/...` (ffmpeg 8.x system header) → silent struct-ABI mismatch at runtime (`pix_fmt=1` after `avcodec_alloc_context3`). Fix: `target_include_directories(<consumer> BEFORE PRIVATE <vendored_include_dir>)`. **Trap:** future v1.3 plans adding new ffmpeg consumers will re-hit this if not protected. Recommend 14.3-01 ships a `jamwide_use_ffmpeg(<target>)` macro encapsulating the discipline.

**L7. 4-stage GUID-pairing pipeline is OUT OF SCOPE.** ADDENDUM.md and deferred-items.md describe the full NinjamZap design (`accumulating → next → pending → playing`, DS/PREV/no-match GUID matching, `kHoldCapDrop=4`). **None of that lands in 14.3.** This phase only gets unknown-fourCC bytes OUT of Vorbis; receiver still has no video state machine, no per-user buffers, no decoder. Don't pull in `VideoRecvBuffer`/`VideoRecvState` (ninjamzap `njclient.h:343-417`) — those are v1.3 / Item F.2-F.3. Plan task adding 4-stage logic = scope slipped.

**L8. `JAMWIDE_VIDEO_SPIKE` stays OFF by default; new tests go under `JAMWIDE_BUILD_TESTS`.** Existing gate at `CMakeLists.txt:41` keeps `video_spike` off because it requires `juce_video` + camera. New `test_rawdata_api` + `test_rawdata_receive` need neither — they go under the standard `JAMWIDE_BUILD_TESTS` (always-on in CI). Don't accidentally re-gate them under `JAMWIDE_VIDEO_SPIKE`.
