# Phase 14.3, Plan 03: Receive-Path Dispatch Fix Summary

**Surgical receive-path wire-compatibility fix: two new else-if branches
INSERTED ahead of the existing else-if(dib.fourcc) at the BEGIN handler
+ new m_rawdata_downloads GUID-match loop running BEFORE the existing
m_downloads loop at the WRITE handler + 8 in-process unit tests
verifying dispatch correctness and OGGv/FLAC routing untouched.**

## Accomplishments

- **SC-6 closure (the only behavioral change of phase 14.3):** the
  receive-path dispatch fix is now live in `src/core/njclient.cpp` at the
  MESSAGE_SERVER_DOWNLOAD_INTERVAL_BEGIN case body. Non-OGGv / non-FLAC
  fourCCs no longer route to start_decode (Vorbis); they dispatch to
  RawData_Callback if registered, or log+discard otherwise.
- **Landmine L4 closure (INSERT not REPLACE):** the existing
  `else if (dib.fourcc)` branch is preserved verbatim AFTER the two new
  branches; OGGv + FLAC streams continue to enter the existing
  start_decode equivalent (`RemoteDownload::Open` + `m_downloads.Add`)
  exactly as before — verified by `test_oggv_begin_routes_to_existing_
  m_downloads` + `test_flac_begin_routes_to_existing_m_downloads`.
- **Landmine L4 second-exclusion verification:** the new branches
  explicitly exclude BOTH `NJ_ENCODER_FMT_TYPE` (OGGv) AND
  `NJ_ENCODER_FMT_FLAC` (JamWide ships FLAC — NinjamZap excludes only
  OGGv). The FLAC-specific test (`test_flac_begin_routes_to_existing_
  m_downloads`) asserts that FLAC with `RawData_Callback` registered
  still routes to `m_downloads`, not the callback.
- **Landmine L7 closure (no 4-stage pipeline):** no `VideoRecvState`,
  no `VideoRecvBuffer`, no per-user accumulation, no decoder, no UI
  buffer — only the 3-event callback dispatch. Verified by grep:
  ```
  grep -cE 'VideoRecvState|VideoRecvBuffer|m_video_recv_cs|
    append_active|m_sync_interval_cnt' src/core/njclient.cpp → 0
  ```
- **WRITE-handler ordering correct:** the new `m_rawdata_downloads`
  loop (line 2349) runs BEFORE the existing `m_downloads` loop (line
  2384). On RawData match, `matched = true` is set and the existing
  m_downloads loop is skipped (cheap insurance against T-14.3-20 GUID
  collisions). The DOWNLOAD_TIMEOUT sweep is preserved inside the
  `if (!matched)` block.
- **VDO.Ninja byte-identity (SC-7):** `git diff -- juce/video companion`
  returns 0 bytes; the existing video pipeline is untouched.
- **No audio-encoder regression (SC-7 indirect):** `git diff -- src/
  core/njclient.cpp | grep -E '^[-+].*MAX_ENC_BLOCKSIZE|m_enc->Encode|
  m_enc->Available' | wc -l → 0` — audio-encoder loop bytes-identical.
- **Full ctest suite passes** (excluding pre-existing failures in
  test_encryption and test_flac_codec documented in `deferred-items.md`):
  13/13 tests pass after this plan; the 2 pre-existing failures predate
  base commit `dd9f6d1`.

## Deviations from Plan

None — plan executed exactly as written. One structural note:

- **Test dispatcher takes primitive fields, not mpb structs.** The plan
  suggested adding `void DispatchTestServerMessage(int msg_type, const
  mpb_server_download_interval_begin& dib)` or similar. We instead
  shipped `DispatchTestServerDownloadIntervalBegin(guid, fourcc, chidx,
  username, estsize)` taking primitive fields — same observable
  behavior, but `njclient.h` does NOT need to include `mpb.h`. The
  alternative (mpb-struct argument) would have forced an include
  rotation and is structurally invisible to the test surface. Listed
  here for completeness; the plan's <action> field allowed either
  approach ("Alternatively expose a friend-class declaration for the
  test" — both options were on the table).
