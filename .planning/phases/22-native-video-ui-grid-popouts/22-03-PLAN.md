<objective>
Build the popout surfaces (per-peer DocumentWindow + detached-grid DocumentWindow) and the placeholder cards that fill the corresponding slot in the in-main-view band when a popout is open. Wire the editor as the owner/controller, with `onPeerPopoutRequested` from the band triggering popout creation and bring-back from the placeholder card triggering destruction. Covers DISP-02 (per-user popout DocumentWindow, multi-monitor friendly) and DISP-03 (grid + popouts coexist via independent Subscriptions per Phase 21 D-06).

Purpose: This is the multi-window surface layer. The risky parts are (1) the popout-vs-band placeholder state machine (4-state truth table per RESEARCH Open Question 3), (2) the multi-monitor bounds clamp on popout open (T-22-MM mitigation), and (3) the lifetime/UAF surface for popouts holding Subscriptions while their parent editor tears down. Each popout window holds its own `RemotePeerTile` with its own `Subscription` — Phase 21 D-06's multi-listener-per-sink contract makes this safe but the planner must declare the popout's child tile as the LAST owned object so its dtor runs before the window's chrome.

Output: 8 new files (4 window/card pairs of .h/.cpp) + 2 modified surfaces (VideoGridBand needs placeholder support; JamWideJuceEditor needs popout map ownership + bring-back controllers) + 1 new test file. After this plan, with the band visible, clicking `↗` on a peer tile opens a popout window; the in-band slot becomes a "Popped out →" placeholder; clicking the placeholder destroys the popout and restores the live tile.

**W5 plan-size note (per checker iter 1):** Plan size accepted at 4-task threshold (3 auto + 1 checkpoint, 14 files modified). Splitting would fragment the popout-window + placeholder-card + bring-back-controller + lifetime-test contract into two interdependent half-plans that share state machines and the same files (VideoGridBand.cpp would be modified in both halves). The popout/placeholder/bring-back triad is a single testable surface; the checkpoint UAT cell exercises all four behaviours together. Sub-50% context target is preserved because Task 1 (windows) and Task 2 (placeholders + editor controller) are sequential and Task 3 (lifetime test) operates in an isolated test TU.
