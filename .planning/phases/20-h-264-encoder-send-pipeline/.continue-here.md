- [ ] CONSTRAINT: **Unit tests with synthetic fixtures cannot replace happy-path UAT against a real public NinjamZap server.** Five distinct wire-format bugs landed and passed Phase 20 unit tests because `feedRawBgraForTest` fed cfg-sized BGRA (bypassing the lazy-sws path) and `nalStreamContainsIdr` scanned for Annex-B start codes (bypassing the AVCC/Annex-B distinction). Each bug only surfaced via tcpdump + byte-level comparison against the canonical NinjamZap upstream spec.
- [ ] CONSTRAINT: **NINJAM/NinjamZap server anonymous channel cap is 2 by default** (`MaxChannels 32 2` in `ninjamzap-server/configs/default-2050.cfg`; `g_config_maxch_anon = 2` hardcoded in `ninjamsrv.cpp:636`). JamWide's 5-channel registration (Ch1-4 + Instatalk) is silently truncated server-side; only the first 2 records reach other peers. **Any v1.3-beta channel-layout decisions must respect this constraint** — full multi-bus mixing requires authenticated or self-hosted servers.

**Do not proceed until both boxes are checked.**

## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| Plan must_have wire-format wording not verified against upstream byte-spec | Plan 20-02 said "[4B BE prefix=20][4B BE counter][16B GUID]" (24-byte marker) and "raw [SPS-NAL][PPS-NAL] concatenation, no length prefix". Upstream `ninjamzap-core/docs/VIDEO_SYNC.md` §6 says "20 bytes marker = [4B BE counter][16B GUID]" and §7 says "[2B BE SPS len][SPS][2B BE PPS len][PPS]". Both deviations broke the web viewer's decoder. | blocking | For any phase touching a third-party wire protocol: cite the canonical spec by URL and section number in plan must_haves; cross-AI plan review must verify byte-for-byte conformance, not just "the test passes". |
| Unit-test fixture bypasses production data shape | `test_video_encoder.cpp::feedRawBgraForTest` fed cfg-sized BGRA (320×240) — matched the broken sws_ identity-scale (cfg→cfg), masking that production camera frames arrive at native resolution (640×480 / 1280×720). | blocking | Add a wire-conformance test that captures real outbound bytes and asserts shape against VIDEO_SYNC.md byte-by-byte. Synthetic fixtures must vary across production-realistic resolution + format combinations. |
| Encoder Annex-B output wrapped as if AVCC | libopenh264 / libavcodec emit Annex-B (`00 00 00 01` start codes between NALs). drainEncoder_ passed the raw packet directly to publishEncodedNal_ which then got AVCC-framed by Plan 20-02's QueueVideoFrame. Result: wire stream was `[4B len][00 00 00 01 NAL_header NAL_data 00 00 00 01 ...]` — double-framed garbage that the web decoder rejected. | blocking | When porting between codec framing conventions, walk the source format and emit one NAL per publish call after stripping start codes — never assume the encoder output matches the target wire framing without verification. |
| `flags & 0x10` server-visible but client-side audio pipeline ignores it | Plan 20-03 set `flags=0x10` on chidx=1 via `SetLocalChannelInfo(1, "video", flags=0x10)` so the SERVER sees a video-only channel, but JamWide's own `process_samples` and `on_new_interval` continued to encode audio Ch2 on chidx=1, colliding wire-side with the H264 video stream. NinjamZap canonical pattern per VIDEO_SYNC.md §7: "the client's audio pipeline skips it in both on_new_interval() and process_samples()". | blocking | When introducing a new channel-purpose flag, audit ALL local-channel iterations and add the skip guard symmetrically. Don't rely on server-side metadata to fix client-side encoder behavior. |
| Plan landed with "encoder works in isolation" verification, integration with real camera path never tested | Plan 20-01's `test_video_encoder.cpp` passed all 5 sub-tests. The encoder works correctly when fed synthetic BGRA. But the integration with `JamWideFrameDistributor` (which delivers real camera frames at native resolution) was never exercised end-to-end before Plan 20-03 ran the UAT. | advisory | Phase-level "encoder + camera path + state machine" integration test should run end-to-end before declaring a plan complete. Plan 20-03's `test_processor_video_lifecycle` was lifecycle-only, not data-path. |

Tonight's diagnostic session uncovered 5 distinct wire-format bugs through tcpdump capture + byte-by-byte comparison against the upstream NinjamZap spec. Each bug was localized: 10-50 lines of code per fix. The deep wire parser at `/tmp/parse-wire-deep.py` proved its worth — without it the Annex-B/AVCC double-framing bug would have been impossible to spot.

The pattern across all 5 bugs is the same: **synthetic unit-test fixtures don't exercise the production data shape**. This is exactly what the user's `feedback_uat_scope_redflags` memory keeps surfacing. The remediation isn't more unit tests — it's a wire-conformance test that captures real outbound bytes and asserts against the spec.

Mental model of the encoder's wire path after all fixes:
1. Camera (JUCE CameraDevice) delivers BGRA at native resolution → JamWideFrameDistributor
2. Distributor fans out to subscribers; Openh264Encoder::onFrame queues into ring slab
3. Encoder thread picks up slot; lazy-recreates sws_ if needed; sws_scale to YUV420P at cfg dims; avcodec_send_frame
4. drainEncoder_ pulls each Annex-B packet, splits on `00 00 00 01` start codes, emits one publishEncodedNal_ per NAL with raw bytes
5. NJClient::QueueVideoFrame wraps each NAL with [4B BE len][NAL] AVCC framing via two RawDataSendWrite calls
6. NJClient::on_new_interval emits per-interval [BEGIN][20B marker][SPS/PPS chunk][END] under whole-block m_video_cs; Task 0 ensures the audio Local_Channel at chidx=1 doesn't also produce OGGv

Expected wire shape (per VIDEO_SYNC.md §7, after GUID-based receiver reassembly):
- Bytes 0-3: BE u32 interval counter
- Bytes 4-19: audio_ch0_guid (16 bytes, all-zero NONE-match if no audio Ch0 with valid GUID)
- Bytes 20-21: 2B BE SPS length
- Bytes 22-22+SPS_len: SPS NAL (no start code)
- Then 2B BE PPS length
- Then PPS NAL
- Then per-frame: 4B BE AVCC length + raw NAL bytes
</context>
