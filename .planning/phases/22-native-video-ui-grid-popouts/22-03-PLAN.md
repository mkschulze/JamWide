<objective>
Build the popout surfaces (per-peer DocumentWindow + detached-grid DocumentWindow) and the placeholder cards that fill the corresponding slot in the in-main-view band when a popout is open. Wire the editor as the owner/controller, with `onPeerPopoutRequested` (typed `VideoPopoutTarget` per codex M5) from the band triggering popout creation and bring-back from the placeholder card triggering destruction. Covers DISP-02 (per-user popout DocumentWindow, multi-monitor friendly) and DISP-03 (grid + popouts coexist via independent Subscriptions per Phase 21 D-06).

Purpose: This is the multi-window surface layer. The risky parts are (1) the popout-vs-band placeholder state machine — codex H3 mandates an explicit 4-state truth table for tile `↗` semantics, (2) the multi-monitor bounds clamp on popout open (T-22-MM mitigation), (3) the lifetime/UAF surface for popouts holding Subscriptions while their parent editor tears down, and (4) keeping the main band and the detached band's inner band synchronized so the user sees consistent placeholder state (codex M7).

**Codex review closures applied:**
- **H2 (juce::HashMap — NARROWED in iter-2):** `remotePopouts_` and `peerPlaceholders_` are `std::unordered_map<juce::String, std::unique_ptr<T>>`. The original codex H2 ("`std::unordered_map<juce::String, ...>` may not compile") was over-broad for THIS codebase — `juce/midi/MidiMapper.h:105` already proves `std::unordered_map<juce::String, int>` compiles cleanly (JUCE 8 ships `std::hash<juce::String>`). H2 is narrowed to copyable value types where iteration determinism matters for serialized output (Plan 22-04's `popoutBoundsMap` keyed `juce::Rectangle<int>`). `juce::HashMap` cannot hold move-only `std::unique_ptr` because its `set()` does copy-assign (`getReference(newKey) = newValue;` at `libs/juce/modules/juce_core/containers/juce_HashMap.h:244`) AND it has no `.find()` returning iterator AND `operator[]` returns ValueType by value (line 182-190) — all three fail template instantiation on move-only types.
- **H3 (4-state truth table — explicit semantics):** Tile `↗` clicked while popout exists-and-hidden RE-SHOWS the popout (no destroy). The destroy path is exclusively via placeholder card click ("bring back"). All four states covered by Task 3 tests.
- **M5 (typed callback):** Editor's `openOrToggleRemotePopout(jamwide::VideoPopoutTarget t)` switches on `t.kind` — Self branch routes to `drivePreviewWindowVisibility`; RemotePeer branch operates on `t.username`. NO `kSelfTileSentinel`/`"__self__"` comparison.
- **M7 (detached-grid sync):** `DetachedGridWindow.h` exposes `getGridBand()` accessor. Editor's bring-back / open-popout paths call `setPeerPoppedOut` on BOTH bands so placeholder state stays consistent. DetachedGridWindow constructs its inner band with `VideoGridBand::Mode::DetachedBand` per Plan 22-02 Task 1 — inner band suppresses its own `↗` detach affordance (recursive detach makes no sense).

Output: 8 new files (4 window/card pairs of .h/.cpp) + 2 modified surfaces (VideoGridBand needs placeholder support; JamWideJuceEditor needs popout map ownership + bring-back controllers + M7 dual-band sync) + 1 new test file. After this plan, with the band visible, clicking `↗` on a peer tile opens a popout window; the in-band slot becomes a "Popped out →" placeholder; clicking the placeholder destroys the popout and restores the live tile. Clicking the same tile `↗` while the popout is hidden re-shows it (codex H3).

**W5 plan-size note (per checker iter 1):** Plan size accepted at 4-task threshold (3 auto + 1 checkpoint, 14 files modified). Splitting would fragment the popout-window + placeholder-card + bring-back-controller + lifetime-test contract into two interdependent half-plans that share state machines and the same files (VideoGridBand.cpp would be modified in both halves). The popout/placeholder/bring-back triad is a single testable surface; the checkpoint UAT cell exercises all four behaviours together. Sub-50% context target is preserved because Task 1 (windows) and Task 2 (placeholders + editor controller) are sequential and Task 3 (lifetime test) operates in an isolated test TU.
