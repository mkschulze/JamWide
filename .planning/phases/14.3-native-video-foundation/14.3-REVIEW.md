**Reviewed:** 2026-05-15

## Summary

Phase 14.3 ships three sub-deliverables: LGPL ffmpeg vendoring infrastructure (14.3-01),
the RawData send-side SPSC scaffolding with NJClient::RawDataSendBegin/Write (14.3-02),
and the receive-path BEGIN/WRITE dispatch INSERT branches (14.3-03). The cmake,
shell, and C++ code is architecturally sound. Landmines L2, L4, L6, L7, and L8 are
all correctly mitigated (L8's GetStatus check is implicit via Run()'s early return at
line 1675, not inline at the drain entry, which is structurally correct).

Two blockers were found: an OOM crash path in RawDataSendWrite due to unchecked
WDL_HeapBuf::Resize, and a dead-code/misleading-comment defect where is_video_fourcc()
is declared with false attribution to callers that do not use it, creating a
maintenance trap. Three warnings cover CI test execution gaps (14.3-02/03 tests
built but never run), an ambiguous shell case pattern for Windows, and a counter
semantic conflation. Three info items address minor quality issues.

## Critical Issues

### CR-01: RawDataSendWrite — WDL_HeapBuf::Resize() unchecked; OOM causes memcpy(NULL) crash

**File:** `src/core/njclient.cpp:3025-3027`

**Issue:** `WDL_HeapBuf::Resize(dataLen)` returns `m_buf` (which is `NULL` for a freshly
constructed `WDL_HeapBuf`) on allocation failure, without updating `m_size`. On the next
line, `buf->Get()` calls `return m_size ? m_buf : NULL` — returning `NULL` because `m_size`
was never updated. `memcpy(NULL, data, dataLen)` is undefined behavior and a guaranteed
crash on all major platforms under memory pressure. Per `wdl/heapbuf.h:183-188`:

```c
if (!(nbuf=malloc(newalloc)))
{
    // ...
    return m_size?m_buf:0; // failed, do not resize
}
```

A newly constructed `WDL_HeapBuf` has `m_size=0`, so OOM returns `0` (null). `Get()`
then also returns null. The subsequent `memcpy` dereferences it.

**Fix:**
```cpp
// Replace at njclient.cpp:3025-3028:
WDL_HeapBuf* buf = new WDL_HeapBuf;
if (!buf->ResizeOK(dataLen)) {
    // Allocation failed — treat as a drop with log.
    delete buf;
    m_rawdata_sendq_overflows.fetch_add(1, std::memory_order_relaxed);
    writeLog("RawDataSendWrite: OOM allocating %d-byte payload — dropped\n", dataLen);
    return;
}
memcpy(buf->Get(), data, (size_t)dataLen);
item.payload = buf;
```

`ResizeOK` is defined at `wdl/heapbuf.h:59` and returns `NULL` on failure without
crashing.

### CR-02: is_video_fourcc() is dead code in production builds; comment falsely attributes callers

**File:** `src/core/njclient.cpp:230-246`

**Issue:** The block comment at lines 230-233 states:

> "only the run-thread drain and the 14.3-03 receive-dispatch INSERT branch consume this"

Neither claim is true. Searching all call sites:
- **Run-thread drain** (lines 2817-2875): dispatches on `item.type` (0=begin, 1=data),
  never calls `is_video_fourcc`.
- **14.3-03 INSERT branch** (lines 2229-2254): uses `fourcc != NJ_ENCODER_FMT_TYPE &&
  fourcc != NJ_ENCODER_FMT_FLAC` — a codec-agnostic exclusion, not `is_video_fourcc`.
- **Sole actual caller**: `NJClient::IsVideoFourcc()` at line 3053, gated under
  `#ifdef JAMWIDE_BUILD_TESTS`. In production builds this wrapper is compiled out.

`is_video_fourcc` is therefore **dead code in every production build**. The false comment
is a maintenance trap: a future developer adding a dispatch caller expecting
video-only semantics (H264/VP8/MJPG) would unknowingly bypass the OGGv/FLAC audio exclusion,
breaking audio playback for Vorbis/FLAC streams (Landmine L4 violation). The dispatch
is intentionally codec-agnostic (routes all non-audio fourccs), which is correct, but the
function name and comment teach the wrong thing.

**Fix:** Update the comment to reflect reality and remove the false attribution:

```cpp
// File-static helper: returns true for the three currently-recognized video
// fourCCs (H264, VP8-with-trailing-space, MJPG). Used ONLY from the
// JAMWIDE_BUILD_TESTS path (NJClient::IsVideoFourcc wrapper) for unit-test
// coverage of the is_video_fourcc helper itself.
//
// NOT called from the receive-path dispatch (njclient.cpp:2229) or the
// run-thread RawData drain (njclient.cpp:2817). The dispatch condition
// is intentionally codec-agnostic: any fourcc that is not NJ_ENCODER_FMT_TYPE
// and not NJ_ENCODER_FMT_FLAC routes to RawData_Callback when registered.
```

If `is_video_fourcc` should guard the dispatch in a future revision, that wiring
must be added explicitly to the dispatch condition at line 2229. Do not assume the
function is already wired.

### WR-01: CI executes only ffmpeg_link_smoke; test_rawdata_send and test_video_fourcc tests are built but never run

**File:** `.github/workflows/juce-build.yml:81`

**Issue:** The macOS CI job configures with `-DJAMWIDE_BUILD_TESTS=ON -DJAMWIDE_VIDEO_SPIKE=ON`
(lines 71-72), which builds `test_rawdata_send` (rawdata_send_roundtrip) and `test_video_fourcc`
(video_fourcc) alongside `test_ffmpeg_link` (ffmpeg_link_smoke). However the ctest invocation
is:

```yaml
run: cd build && ctest -R ffmpeg_link_smoke --output-on-failure
```

The `-R ffmpeg_link_smoke` regex filter selects only the ffmpeg smoke test. The 14.3-02 and
14.3-03 unit tests — which cover the SPSC send-queue round-trip, chunking, overflow counting,
Landmine L4 exclusion, and disconnect discard — are **never executed in CI**. A regression
in any of these behaviors would pass CI undetected.

**Fix:** Run all three test suites in a single ctest step:

```yaml
- name: Run Phase 14.3 unit tests
  run: |
    cd build
    ctest -R "ffmpeg_link_smoke|rawdata_send_roundtrip|video_fourcc" \
          --output-on-failure
```

Or run all tests (`ctest --output-on-failure`) and accept that the two pre-existing
failures (test_encryption, test_flac_codec) are expected, using `--ignore-return-code`
with explicit listing, or `PASS_REGULAR_EXPRESSION` on those two.

### WR-02: MINGW case-pattern in build_ffmpeg_lgpl.sh is syntactically ambiguous and accidentally correct

**File:** `scripts/build_ffmpeg_lgpl.sh:76`

**Issue:** The Windows case arm at line 76 is:

```bash
MINGW64_NT-*"|x86_64"|MSYS_NT-*"|x86_64"|CYGWIN_NT-*"|x86_64")
```

The shell parses this as six alternating patterns: `MINGW64_NT-*`, `"x86_64"`, `MSYS_NT-*`,
`"x86_64"`, `CYGWIN_NT-*`, `"x86_64"`. The first pattern (`MINGW64_NT-*`) successfully
matches `"MINGW64_NT-10.0-19041|x86_64"` because the unquoted glob `*` consumes the `|x86_64`
suffix. This is accidental: the intent was to match `"MINGW64_NT-*|x86_64"` as a compound
OS-pipe-ARCH string (matching the first two arms' quoting style). The current form would
also match `"MINGW64_NT-10.0-19041|arm64"` if such a platform existed.

Compare to the correctly-quoted prior arms:
```bash
"Darwin|x86_64")   # quotes encompass the | separator
"Darwin|arm64")
```

**Fix:**
```bash
"MINGW64_NT-*|x86_64"|"MSYS_NT-*|x86_64"|"CYGWIN_NT-*|x86_64")
```

Quoting each arm individually ensures the pipe character is part of the match string
and the arch suffix is enforced, not swallowed by the wildcard.

### WR-03: Overflow counter conflates queue-full drops with disconnect discards

**File:** `src/core/njclient.cpp:2819-2822`, `src/core/njclient.h:746-755`

**Issue:** `m_rawdata_sendq_overflows` is bumped in two distinct situations:

1. **Queue-full drop** (lines 3001, 3036): `try_push` fails because the SPSC ring is at
   capacity — a genuine overflow meaning the producer is too fast for the drain.
2. **Disconnect discard** (line 2821, Pattern C): the ring was successfully written but
   `m_netcon` is null when the drain runs, so items are discarded.

These are different failure modes with different remediation (capacity vs connection state).
The post-UAT invariant `GetRawDataSendQueueOverflowCount() == 0` documented in
`spsc_payloads.h:385-386` and `njclient.h:753` becomes unactionable because a UAT run
involving any Disconnect/Reconnect cycle (normal use) will produce non-zero counts even with
a correctly-sized queue. `test_rawdata_send.cpp:375-380` explicitly validates that the
disconnect path bumps the counter, cementing the conflation as tested behavior.

**Fix:** Add a separate `m_rawdata_sendq_discards` atomic counter for Pattern C discards,
leaving `m_rawdata_sendq_overflows` strictly for `try_push` failures. Update
`GetRawDataSendQueueOverflowCount()` documentation to state it covers only try_push failures,
and add `GetRawDataSendQueueDiscardCount()` for the disconnect path. Update the test and the
post-UAT invariant accordingly.

### IN-02: test_is_video_fourcc_vp8_trailing_space — FAIL branches lack return

**File:** `tests/test_rawdata_send.cpp:305-307`

**Issue:** The else-if and else `FAIL()` branches in `test_is_video_fourcc_vp8_trailing_space`
do not call `return` after `FAIL()`. All other test functions in both `test_rawdata_send.cpp`
and `test_video_fourcc.cpp` consistently call `return` after `FAIL()` to prevent
fall-through to `PASS()`. In this specific function the fall-through is harmless (the
function exits normally without calling `PASS()`, so `tests_passed` is not incorrectly
incremented), but the inconsistency is a maintenance hazard — a future refactor merging
the branches could accidentally reach `PASS()` after a failure path.

**Fix:**
```cpp
} else if (!vp8_space) {
    FAIL("VP8 trailing-space variant should be recognized as video");
    return;
} else {
    FAIL("VP8 with NUL trailing byte should NOT be video (tightened from NinjamZap)");
    return;
}
```

### IN-03: verify_ffmpeg_lgpl.sh silently passes ldd "not found" entries on Linux

**File:** `scripts/verify_ffmpeg_lgpl.sh:119-124`

**Issue:** The ldd check at line 119 pipes through `awk -F'=>' '{print $2}'` which
extracts the path after `=>`. For a missing dependency (`libfoo.so.1 => not found`),
`$2` is `" not found"` and `awk '{print $1}'` yields `"not"`. The grep for
`/usr/local|/opt|/home` does not match `"not"`, so a missing dependency passes silently.
The check was intended to catch contaminated dependencies, but a completely absent dependency
(e.g., a misconfigured patchelf run that broke a NEEDED entry) would not be surfaced.

**Fix:** Add an explicit "not found" check:

```bash
# Catch both bad-path deps and missing deps
BAD=$(echo "$LDD_OUT" | grep -E '^/usr/local|^/opt|^/home|^not$' || true)
```

Or use `ldd --verbose` with the raw output and check for `"not found"` strings directly:
```bash
if ldd "$D" 2>/dev/null | grep -q "not found"; then
    BAD_DEPS+="$D: has 'not found' deps\n"
fi
```
