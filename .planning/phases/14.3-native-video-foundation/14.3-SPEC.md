# Phase 14.3: Native Video Foundation — SPEC

## What this phase delivers

Three deliverables, all additive (no behavioral change to JamWide's existing video):

1. **Cross-platform LGPL ffmpeg + Cisco openh264 vendoring** under `libs/ffmpeg/{macos-arm64,macos-x86_64,linux-x86_64,windows-x86_64}/{lib,include}/`, produced reproducibly by `scripts/build_ffmpeg_lgpl.sh` with the LGPL-discipline flags `--disable-gpl --disable-libx264 --enable-libopenh264 --disable-xlib --disable-libxcb --disable-sdl2`. CI verifies: (a) no x264 strings in any vendored dylib; (b) macOS dylibs have no spurious `/usr/local/opt/...` deps via `otool -L`.

2. **Codec-agnostic transport API** in JamWide's NJClient mirroring NinjamZap's working pattern:
   - Send side: `RawDataSendBegin(outGuid[16], fourcc, chidx, estsize)` + `RawDataSendWrite(guid[16], data, len, isEnd)`. Models `ninjamzap-core/njclient.cpp:2047-2065`.
   - Receive side: `RawDataCallback` with `eventType ∈ {begin, data, end}`, `guid[16]`, `fourcc`, `username`, `chidx`, `data`, `dataLen`. Models `ninjamzap-core/njclient.h:205-212`.
   - Thread-safe send queue (per spike Q3 finding — `Net_Connection::Send` is NOT thread-safe; needs SPSC or mutex around the producer call). Use SPSC for consistency with Phase 15.1 architecture.

3. **Receive-path dispatch fix** at `src/core/njclient.cpp:2148`. Today, any non-FLAC/non-Vorbis fourCC silently routes to the Vorbis decoder (RESEARCH §6 documents this as a wire-compatibility BUG). After this phase, unknown-fourCC streams dispatch to `RawDataCallback` if registered, otherwise log + discard. Plus an `is_video_fourcc()` helper for `{H264, VP8 , MJPG}` so future code can identify video streams cleanly.

## Why this phase belongs in v1.1 (not v1.3)

The user direction (2026-05-15) is to insert a foundation phase in the existing v1.1 milestone, then move the rest of the native-video work into a new v1.3 milestone. Rationale:

1. v1.1 is thematically "OSC + Video" — vendoring video infrastructure fits.
2. v1.1 has all its other planned phases done (`[x]`); 14.3 is the last work needed before formal milestone closure.
3. 14.3 is small and additive — does not block v1.1 closure if it ships first.
4. Vendoring + RawData API are foundational primitives that v1.3 needs to start with anyway. Landing them in v1.1 means v1.3 starts with a usable transport substrate, not a green field.
5. v1.1 closure can then happen normally via `/gsd-complete-milestone` after 14.3 ships.
