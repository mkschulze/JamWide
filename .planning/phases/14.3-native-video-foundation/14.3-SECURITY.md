### T-14.3-08 — Tampering / Memory-Safety | RawDataItem.payload (owned WDL_HeapBuf*)

| Field | Value |
|-------|-------|
| Disposition | mitigate |
| Status | **CLOSED** (re-audited 2026-05-15) |
| Severity | critical (NULL-deref crash on memory pressure; reachable from any thread that calls RawDataSendWrite) |
| Fix commit | `8e594f8` |

**Declared mitigation (from `14.3-02-PLAN.md` threat row):**
> Ownership protocol locked: producer allocates on RawDataSendWrite; SPSC
> carries the pointer; drain branch deletes after Send; discard branch (null
> m_netcon) deletes without sending; destructor drains and deletes; test
> test_disconnect_drain_and_discard exercises the discard branch. No
> double-delete possible because the drain pops items (try_pop transfers
> ownership out of the ring).

**Re-audit verification:** The full lifecycle ownership chain plus the
previously-missing allocation-failure path now hold:

| Lifecycle stage | Evidence | Status |
|-----------------|----------|--------|
| Producer allocates | `src/core/njclient.cpp:3030` — `WDL_HeapBuf* buf = new WDL_HeapBuf;` | PRESENT |
| SPSC carries the pointer (trivially copyable) | `src/threading/spsc_payloads.h` — POD struct + `static_assert std::is_trivially_copyable_v<RawDataItem>` | PRESENT |
| Drain (send branch) deletes after Send | `src/core/njclient.cpp` Run() drain block — `delete item.payload;` after per-chunk Send loop | PRESENT |
| Discard branch (null m_netcon) deletes | `src/core/njclient.cpp` discard branch — `delete item.payload; m_rawdata_sendq_overflows.fetch_add(...)` | PRESENT |
| Destructor drains and deletes | `src/core/njclient.cpp:1222-1224` — `m_rawdata_sendq.drain([](jamwide::RawDataItem&& item) { delete item.payload; });` | PRESENT |
| **Allocation-failure path (OOM)** | `src/core/njclient.cpp:3031-3039` — `ResizeOK(dataLen)` NULL-check, `delete buf`, overflow counter bump, writeLog, early return | **PRESENT (was MISSING in prior audit)** |
| **Queue-full path** | `src/core/njclient.cpp:3044-3054` — try_push failure: `delete item.payload`, overflow counter bump, writeLog | PRESENT (unchanged from prior audit) |

Detail of the OOM-path fix (per `src/core/njclient.cpp:3026-3041`):

```c
// T-14.3-08 / CR-01: ResizeOK (not Resize) — Resize() returns without
// updating m_size on alloc failure, after which Get() returns NULL and
// the memcpy below would NULL-deref. ResizeOK returns NULL on failure
// and we treat OOM as a send drop (matches the queue-full path below).
WDL_HeapBuf* buf = new WDL_HeapBuf;
if (!buf->ResizeOK(dataLen))
{
  delete buf;
  m_rawdata_sendq_overflows.fetch_add(1, std::memory_order_relaxed);
  writeLog("RawDataSendWrite: OOM allocating %d-byte payload — dropped"
           "%s\n",
           dataLen, isEnd ? " (isEnd)" : "");
  return;
}
memcpy(buf->Get(), data, (size_t)dataLen);
item.payload = buf;
```

**Semantics verified:** `wdl/heapbuf.h:59` defines `ResizeOK`:
```c
void *ResizeOK(int newsize, bool resizedown = true) { void *p=Resize(newsize, resizedown); return GetSize() == newsize ? p : NULL; }
```
On allocation failure, `Resize()` does not update `m_size`, so `GetSize() != newsize`, so `ResizeOK` returns `NULL`. The fix's `if (!buf->ResizeOK(dataLen))` branch therefore fires correctly on OOM.

**Symmetric observability verified:** Both error classes route through the same observability paths:

| Error class | Counter bump | Log call | Cleanup |
|-------------|--------------|----------|---------|
| OOM at allocation time (line 3031) | `m_rawdata_sendq_overflows.fetch_add(1, std::memory_order_relaxed)` at line 3034 | `writeLog("RawDataSendWrite: OOM allocating %d-byte payload — dropped%s\n", ...)` at line 3035-3037 | `delete buf` at line 3033, `return` at line 3038 |
| Queue-full at try_push time (line 3044) | `m_rawdata_sendq_overflows.fetch_add(1, std::memory_order_relaxed)` at line 3049 | `writeLog("RawDataSendWrite: SPSC full (capacity %zu) — dropped %d-byte write%s\n", ...)` at line 3050-3053 | `delete item.payload` at line 3048 |

Same counter, same atomic semantics, same log-style with class-distinguishing prefix ("OOM allocating" vs "SPSC full"). The queue-full path is unchanged from the prior audit (compare prior `delete item.payload; m_rawdata_sendq_overflows.fetch_add(...)` pattern at the same call site).

**T-14.3-08 CLOSED.** The OOM NULL-deref crash path identified by CR-01 is eliminated; the previously-verified lifecycle ownership chain remains intact.

## Accepted Risks Log

These threats were registered at plan-time with disposition `accept`. The
audit confirms the implementation shipped is consistent with the accept
rationale; the risks are accepted in this phase and either inherited by v1.3
or pre-date 14.3.

### AR-1 (T-14.3-02): Cisco openh264 binary trust anchor
- **Decision:** Accept Cisco's distribution channel as the trust anchor for
  the openh264 prebuilt binaries (x86_64 platforms). Cisco's MPEG-LA royalty
  payment is inherited only by Cisco-distributed binaries; rebuilding from
  source forfeits this inheritance (per `14.3-SPEC.md` §"Locked Decisions"
  #5).
- **Residual risk:** If Cisco's GitHub release infrastructure is compromised,
  the vendored binary could carry a backdoor. Mitigated by HTTPS fetch + the
  fact that Cisco's release infra is trusted by ffmpeg upstream + every major
  Linux distro.
- **Exception:** arm64-mac path builds openh264 from source (line 111-133 of
  `scripts/build_ffmpeg_lgpl.sh`) — does NOT inherit Cisco's royalty payment.
  MPEG-LA AVC patent pool registration may be required for commercial
  arm64-mac distribution at scale (>100k licenses/year). Documented inline at
  `scripts/build_ffmpeg_lgpl.sh:22-29`.

### AR-2 (T-14.3-04): configure-flags.txt contains build-host absolute paths
- **Decision:** The literal `./configure` invocation written to
  `libs/ffmpeg/configure-flags.txt:8` includes the build-host's REPO_ROOT
  path (`/Users/cell/dev/JamWide/.claude/worktrees/agent-...`). This is
  intentional — the file is a license-compliance audit artifact per LGPL
  section 6, recording the exact build provenance for reproducibility.
- **Residual risk:** Discloses the developer's local username and worktree
  path. Not a secret; the file is intended to be human-readable in the
  distributed archive.

### AR-3 (T-14.3-05): Build script downloads can hang/fail
- **Decision:** `curl -fsSL` invocations at `scripts/build_ffmpeg_lgpl.sh:142,
  154, 166, 221, 357` have no retry/backoff. This is a once-per-platform
  vendoring driver; failure is recoverable by re-running the script.
- **Residual risk:** Transient network failure aborts the vendoring run mid-
  build. Easily recoverable.

### AR-4 (T-14.3-11): RawData payloads carry opaque bytes (v1.3 → video frames)
- **Decision:** Phase 14.3 ships transport scaffolding only. No payload-
  carrying consumer of the RawData API exists in 14.3 except in-process tests
  (which use synthetic byte arrays). The "video frames containing user's
  camera" payload only materializes in v1.3.
- **Residual risk:** Zero in 14.3. Flagged for v1.3 to couple with Phase 15
  AES-256-CBC payload encryption.
- **Carry forward:** Track as a Phase 15 dependency for v1.3 Native Video
  milestone.

### AR-5 (T-14.3-13): Default-zero RawData_Callback fires before assignment
- **Decision:** Constructor initializes `RawData_Callback=0; RawData_User=0;`
  at `src/core/njclient.cpp:1013-1014`. All production call sites
  (`njclient.cpp:2232,2244,2362,2369`) check `RawData_Callback` non-null
  before invoking. Pattern matches `ChatMessage_Callback` (v1.0, no
  incidents).
- **Residual risk:** A future call site added without the null-check would
  re-introduce this risk. No mechanical enforcement.

### AR-6 (T-14.3-15): Hostile server floods unknown fourCCs to fill m_rawdata_downloads
- **Decision:** `m_rawdata_downloads` is an unbounded `WDL_PtrList` matching
  the pre-existing `m_downloads` pattern at `src/core/njclient.h:858`.
  14.3-03 does not add a timeout sweep equivalent to the `DOWNLOAD_TIMEOUT`
  sweep in the audio path (`src/core/njclient.cpp:2406-2411`).
- **Residual risk:** Server compromise could OOM the client via fourCC flood.
  NINJAM server churn is human-paced; floods imply server compromise.
  Inherited by v1.3 — adding a timeout sweep is a one-liner when video frames
  start flowing.
- **Carry forward:** v1.3 should add a DOWNLOAD_TIMEOUT-equivalent sweep on
  `m_rawdata_downloads`.

### AR-7 (T-14.3-18): RawData_Callback delivers untrusted bytes to consumer
- **Decision:** Callback signature matches NinjamZap verbatim
  (`src/core/njclient.h:629-631`); the callback contract requires consumers
  to validate `dataLen` and `data` pointer before dereferencing. 14.3 only
  ships scaffolding — only test consumers exist in this phase.
- **Residual risk:** v1.3 consumers (H.264 decoder) must enforce input
  validation at the callback site.
- **Carry forward:** v1.3 decoder integration MUST add input validation at
  the RawData_Callback consumer entry point.

### AR-8 (T-14.3-19): Adversarial server sends fourcc=FLAC to bypass dispatch
- **Decision:** `NJ_ENCODER_FMT_FLAC` is in the exclusion set at
  `src/core/njclient.cpp:2230-2231` and 2249-2250. FLAC streams route through
  the existing `else if (dib.fourcc)` branch (lines 2255-2267) unchanged.
  Invalid FLAC frames are handled by the existing v1.0 FLAC decoder behavior.
- **Residual risk:** None new in 14.3 — the FLAC decode path is unchanged.
